LSP: приклади порушень

Принцип підстановки Лісков (LSP) говорить про те, що об’єкти похідного класу повинні без проблем заміняти об’єкти базового класу. Якщо при підстановці нащадка програма починає працювати неправильно або потребує додаткових перевірок, то принцип LSP порушений.

Нижче наведено кілька прикладів порушення цього принципу.

Перший приклад — птахи та політ.
Є базовий клас Bird з методом Fly(). Для більшості птахів це логічно, але якщо створити клас Penguin, який наслідується від Bird, виникає проблема, бо пінгвіни літати не можуть. У результаті метод Fly() або кидає помилку, або нічого не робить. Це порушує LSP, оскільки об’єкт Penguin не може коректно замінити Bird у коді, де очікується можливість польоту.
Проблема виникає через неправильну ієрархію.
Виправити це можна, якщо розділити птахів на тих, що літають, і тих, що не літають, наприклад через окремий інтерфейс Flyable.

Другий приклад — облікові записи користувачів.
Є базовий клас Account з методом Withdraw(), який дозволяє знімати гроші. Якщо створити клас FixedDepositAccount, де зняття коштів заборонене, то метод Withdraw() або не працює, або викидає помилку. У такій ситуації цей клас не може бути повноцінною заміною Account, що також порушує LSP.
Проблема тут у тому, що поведінка базового класу змінюється в нащадку.
Правильніше було б винести зняття коштів в окремий інтерфейс або мати різні типи рахунків без спільного контракту на Withdraw().

Третій приклад — робітники та зарплата.
Є клас Employee з методом CalculateSalary(). Якщо створити клас Intern, який не отримує зарплату, але змушений реалізовувати цей метод, то виникає нелогічна поведінка (повертається 0 або виникає помилка). Такий клас формально наслідується, але логічно не підходить під базовий контракт.
Це порушує LSP, бо Intern не може поводитись так само, як звичайний працівник.
Рішенням може бути розділення на різні типи працівників або використання інтерфейсів для оплати праці.

У всіх наведених прикладах проблема виникає через те, що підкласи не можуть коректно замінити базовий клас без зміни логіки програми. Дотримання LSP допомагає уникати таких ситуацій, робить код більш гнучким і зрозумілим для підтримки.
