Лабораторна робота №20
Тема: SRP: декомпозиція OrderProcessor

Мета роботи
Метою лабораторної роботи є застосування принципу єдиної відповідальності (SRP) шляхом рефакторингу класу OrderProcessor та розділення його функціональності на окремі компоненти.

Початкова реалізація
На початку було створено клас OrderProcessor, який порушує принцип SRP, оскільки він одночасно відповідав за валідацію замовлення, його збереження, відправку email-повідомлення клієнту та зміну статусу замовлення.

Рефакторинг відповідно до SRP
Для дотримання принципу єдиної відповідальності функціональність класу OrderProcessor була розділена на окремі інтерфейси та їх реалізації. Було створено інтерфейси IOrderValidator, IOrderRepository та IEmailService, кожен з яких відповідає лише за одну конкретну задачу.

Для координації роботи цих компонентів було реалізовано клас OrderService, який отримує всі залежності через конструктор, що відповідає принципу Dependency Injection.

Демонстрація роботи
У методі Main було створено валідне та невалідне замовлення. Для валідного замовлення відбувається успішна валідація, збереження та відправка email-повідомлення. Для невалідного замовлення процес обробки зупиняється на етапі валідації, що виводиться у консоль.

Висновок
У ході виконання лабораторної роботи було продемонстровано застосування принципу SRP на практиці. Рефакторинг дозволив зробити код більш зрозумілим, гнучким та придатним до розширення без зміни існуючої логіки.
